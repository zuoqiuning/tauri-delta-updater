# Web bundle 热更新：威胁模型与准入门槛

> 状态：**设计评审文档，未实现**。在本文的准入门槛全部满足前，不写任何替换代码。

## 0. 竞品基线

`tauri-plugin-hot-update` 已经实现签名 bundle、原子回滚与无计时器的三态指针。
本设计**不再以“更安全的三态回滚”作为差异化卖点**；必须靠
“清单签名覆盖 URL + web 版本单调性 + asset scope 隔离 + 保留策略”中的
至少 2–3 条具体论证成立，才值得进入实现。逐条对照见本文 §0 的基线分析。

## 1. 范围

目标：让同一个引擎在不重启原生进程的前提下替换前端资源（JS / CSS / HTML / 静态资源），复用现有的清单签名、哈希校验、暂存与回滚契约。

非目标：

- 不接管 Service Worker / 浏览器缓存策略；
- 不执行未签名的远程代码；
- 不把前端 bundle 的“版本”与原生二进制版本混为一谈；
- 不在本轮实现任何替换逻辑。

## 2. 资产与信任边界

| 资产 | 信任来源 | 失败后果 |
|---|---|---|
| 前端 bundle 字节 | 清单签名覆盖的哈希 | 任意 JS 执行 |
| bundle 下载 URL | **必须**被清单签名覆盖 | 攻击者可换成自洽的恶意 URL + 哈希 |
| 激活指针（当前使用哪个 bundle） | 本地状态文件 + 原子切换 | 半新半旧、启动白屏、回滚失败 |
| 前端资源目录 | 本地文件系统权限 | 路径穿越写入任意位置 |
| 清单本身 | 应用内置公钥验签 | 降级重放、URL 替换 |

核心原则：**哈希只证明“这份字节没变”，清单签名才证明“这份字节和这个 URL 是发布者选的”。** 只签哈希不签 URL 的方案不成立。

## 3. 威胁清单

### T1. 清单替换 / 降级重放

攻击者控制 CDN 或更新端点，返回一份旧版本清单，把前端回滚到含已知漏洞的 bundle。

- 控制：清单必须签名；验签后按语义化版本执行单调性判断；重放旧清单返回 `UpToDate`，不得激活旧 bundle。
- 与原生更新共用同一套 `is_newer_than` / `min_version` 判据，不另写一套。

### T2. 只签哈希、不签 URL

攻击者把清单里的 `bundle_url` 指向自己的恶意 bundle，并填入对应的正确哈希。客户端校验哈希会通过。

- 控制：清单签名覆盖 `bundle_url`、`bundle_hash`、`version` 三者；三者任一改变都必须验签失败。
- 禁止“先下载再看清单”或“清单只给哈希、URL 由客户端拼”的设计。

### T3. 路径穿越 / 符号链接逃逸

解压时出现绝对路径、`..`、盘符、NUL、符号链接或硬链接，导致写入 bundle 目录之外。

- 控制：复用 `core::bundle::archive` 的路径校验（拒绝绝对路径、`..`、盘符、非法段）；解压前逐项校验，解压后再次校验；拒绝符号链接与硬链接；暂存目录必须是工作目录下的新建目录，不能是用户指定路径。
- 不允许“先解压再检查”。

### T4. 解压炸弹 / 资源耗尽

恶意 bundle 声明巨大的解压后体积或海量小文件，耗尽磁盘/inode。

- 控制：从签名清单读取 `bundle_size` / 文件数上限；超过上限直接拒绝；流式解压，不把整包读进内存；与原生补丁相同的 2 GB 文件上限与磁盘预检。

### T5. 半新半旧 / 非原子激活

切换过程中断电或崩溃，目录里同时存在新旧两套资源，或激活指针指向一个不完整目录。

- 控制：bundle 必须解压到**版本命名的独立目录**（如 `web/1.2.3-<hash>/`），完整校验后再原子更新“当前版本指针”（文件内容为目录名，或固定软链接）。
- 激活指针只指向已完整校验的目录；旧目录在确认新版本可用前不得删除。
- 回滚 = 把指针指回上一个完整目录；不需要重新下载。

### T6. 启动确认语义混用

前端 bundle 的“生效”不需要重启进程，直接复用 `staged → booting → committed` 会把原生启动状态机污染。

- 控制：为 Web bundle 单独定义 `staged → activated → confirmed`：
  - `staged`：新目录已校验，指针未切换；
  - `activated`：指针已切换，但尚未收到前端健康确认；
  - `confirmed`：宿主（或前端）显式确认关键页面可加载。
- 失败/超时回到上一个 `confirmed` 目录；状态文件独立命名，不与原生 `tdx_update_state` 共用。
- `Diagnosis` 可以同时暴露两类状态，但字段必须分开，避免“原生已提交”被误读成“前端已确认”。

### T7. 校验与读取的 TOCTOU

校验完成后、激活前，目录内容被本地进程改写。

- 控制：激活前对目录做一次完整哈希复核；目录权限限制为当前用户；激活指针切换是最后一步，切换后不再改写目录内容。
- 与原生 `VerifiedArtifact::verify_integrity()` 同等级别，不接受“校验一次就够”。

### T8. Asset protocol / 来源边界

前端资源通过 Tauri asset protocol 或 http 协议加载，若作用域过宽，可能读到工作目录之外的任意文件。

- 控制：只注册指向“当前 bundle 根目录”的 asset scope；路径必须规范化后仍在根目录内；禁止把整个用户缓存目录暴露给前端。
- 需要确认 Tauri v2 的 asset protocol scope 是否支持运行期切换；若不支持，必须在设计阶段换方案（例如固定根目录 + 版本子目录）。

### T9. CSP 与远程代码

bundle 激活后，前端仍可能从网络加载未经签名的脚本。

- 控制：文档要求宿主保持严格 CSP；本引擎只保证“本地 bundle 字节是发布者签发的”，不承诺拦截页面内主动发起的远程请求。

### T10. 缓存与回滚的幂等性

重复激活、并发激活、回滚后再次激活必须幂等。

- 控制：激活操作持有与原生更新相同的跨进程锁；指针写入原子替换；同一版本目录存在且哈希一致时直接复用，不重复下载。

## 4. 准入门槛（全部满足才进入实现）

1. 清单签名覆盖 `bundle_url`、`bundle_hash`、`version`，并有单元测试证明“改 URL / 改哈希 / 改版本”三者任一都会验签失败。
2. 解压路径校验复用 `core::bundle` 的现有规则，并有针对绝对路径、`..`、盘符、符号链接的负向测试。
3. 版本目录 + 指针切换的原子性有跨平台测试（Windows 目录替换、macOS/Linux rename）。
4. 独立的 `staged → activated → confirmed` 状态机，不复用原生启动指针；状态文件与 `Diagnosis` 字段分开。
5. 磁盘上限、文件数上限、解压体积上限与现有原生路径一致。
6. 一份明确的 asset scope 方案，确认 Tauri v2 可以在运行期切换或使用固定根目录。
7. 回滚不依赖网络：旧目录在确认前始终保留。
8. 安全评审通过后再写代码；实现顺序为“只读校验 → 暂存 → 切换 → 回滚”，每步单独测试。

## 5. 与现有引擎的复用边界

可以直接复用：

- 清单验签与版本单调性；
- 下载器的断点续传、体积上限、退避重试；
- `core::bundle::archive` 的路径校验与流式哈希；
- 跨进程更新锁；
- `Diagnosis` 的只读快照模式。

不能直接复用：

- 原生替换脚本（PowerShell / sh）与 `.bak` 机制；
- 原生 `staged → booting → committed` 状态文件；
- 原生 `confirm_startup_success` API（语义不同）。

## 6. 明确的非目标

- 不做“远程 URL 直接执行”；
- 不做“无清单、只信任 HTTPS”；
- 不做“前端自行决定加载哪个 bundle”（激活决定权必须在 Rust 侧）。

## 7. Open questions（需要外部评审）

这些问题不解决，就不能进入实现：

1. **asset scope 的作用域**
   Tauri v2 的 asset protocol scope 能否在运行期切换？如果只能全局配置，
   bundle 目录与用户文件是否会被同一个 scope 覆盖？
   候选方案：固定根目录 `web/`，每个版本一个子目录，scope 只指向 `web/`；
   禁止把用户缓存目录整体暴露。

2. **bundle 目录放在 app data 还是 cache**
   app data 不会被清理工具误删，但可能被备份/同步；
   cache 更轻，但可能被系统清理，导致回滚目标消失。
   候选：放 app data，旧版本保留最近 N 个；cache 只放下载中的临时包。

3. **状态指针是否与原生更新共用**
   原生是 `staged → booting → committed`，需要进程重启；
   前端是 `staged → activated → confirmed`，不需要重启。
   候选：独立文件 + 独立 `Diagnosis` 字段，绝不共用，避免语义污染。

4. **“confirmed” 的判定标准**
   谁来确认？宿主 Rust 侧、前端 JS、还是两者都行？
   如果前端可以写 confirmed，一个 XSS 就能把坏 bundle 固定下来。
   候选：只接受 Rust 侧确认（例如关键页面 IPC 健康检查），前端不能直接写状态。

5. **签名粒度**
   清单签一次（覆盖 URL+hash+version），还是 bundle 再单独签一次？
   单独签名会增加发布复杂度，但允许 bundle 独立于原生版本发布。
   候选：第一阶段只签清单；bundle 单独签名作为后续扩展。

6. **bundle 版本与原生版本的单调性**
   前端 bundle 可能有自己的 `1.0.0 → 1.0.1`，与 app 的 `0.2.0` 不同步。
   是否允许 bundle 版本独立递增？重放旧 bundle 清单如何阻断？
   候选：清单内使用独立的 `web_version`，与 app 版本分开比较；
   `min_version` 同样需要作用于 web 版本。

7. **回滚保留数量与磁盘上限**
   保留几个旧 bundle？每个版本的体积上限是多少？
   候选：默认保留 2 个（当前 + 上一个 confirmed），总上限与原生补丁共享磁盘预算。

8. **CSP 与缓存失效**
   激活新 bundle 后，WebView 缓存如何失效？是否要求宿主使用内容哈希文件名？
   候选：bundle 文件名带 hash，入口 HTML 由 Rust 侧注入当前版本路径；
   CSP 保持严格，不允许 `unsafe-eval`。

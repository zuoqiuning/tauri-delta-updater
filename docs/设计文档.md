## 1. 设计目标与取舍

### 1.1 要解决的问题

Tauri 官方 `tauri-plugin-updater` 每次更新都下载完整安装包。典型桌面应用安装包 50–200 MB，即便相邻版本只有几 MB 的差异，用户仍要付出完整下载的流量与等待。

`tauri-delta-updater` 的目标：**只传输差异部分**，同时不牺牲任何安全性。

### 1.2 核心取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 差分算法 | `qbsdiff`（bsdiff 变体） | 比原版 bsdiff 更快、内存更省，且支持并行计算 |
| 清单格式 | 扩展 Tauri `latest.json` | 官方 updater 仍可正常读取全量下载路径，两者可共存 |
| 补丁归属 | 按平台分组 | 不同架构的二进制完全不同，混在一起必然取错 |
| 完整性校验 | SHA-256 双端校验 | 补丁哈希 + 产物哈希，任何一环不符即拒绝 |
| 真实性校验 | Ed25519 清单签名 | 防止中间人篡改 `target_hash` 指向恶意产物 |
| 失败处理 | 自动回滚 + 安全模式 | 更新失败不能把用户卡在无法启动的状态 |
| 接入复杂度 | 一行调用 + 分步底层 API | 简单场景零心智负担，复杂场景完全可控 |

### 1.3 明确不做的事

- **不做跨版本补丁链**。当前只支持"当前版本 → 目标版本"的单跳补丁。跨版本请回退全量下载。
- **不做自增量的元数据更新**（即不拆分"元数据差异"与"数据差异"两阶段）。
- **不接管官方 updater 的全量下载**。全量路径仍由 `tauri-plugin-updater` 负责，本引擎只在有补丁时接管。

### 1.4 定位：增量加速器，而非平行的更新栈

本库与官方 `tauri-plugin-updater` 是**两条腿并存**，不是竞争关系：

```
宿主同时注册官方 updater 与本库
  ├─ 本库命中安全增量 → 接管替换（下载小补丁，本地合并，替换 exe）
  └─ 本库未命中     → FallbackToFullDownload { full_download_url, reason }
                      官方 updater 接手全量下载（它本来就会做的事）
```

**回退不是失败，是正确性优先**。适用边界是显式的运行时判定
（`incremental_fallback_reason`，见 3.8），不是文档里的一行字：

- 补丁基底是运行中的 exe 本身——绕开了"客户端重建字节一致安装包"这个
  最难的工程问题（NSIS solid 压缩、`.app.tar.gz` 的 gzip 参数、squashfs
  布局都不需要复现）；代价是安装/回滚由本库自己扛，因此适用边界必须诚实。
- **Windows 单文件 exe 是甜点区**；AppImage 与 macOS bundle 自动回退
  （见 3.8），不在结构短板上硬扛。

## 2. 整体架构

### 2.1 模块划分

```
tauri-delta-updater
├── core/                     平台无关的核心能力
│   ├── artifacts.rs          临时文件与标志文件的统一命名
│   ├── crypto.rs             TLS 后端懒安装
│   ├── diff.rs               补丁生成与应用
│   ├── disk.rs               磁盘空间查询、临时文件清理
│   ├── downloader.rs         带进度与续传的下载
│   ├── hasher.rs             SHA-256 计算
│   ├── lock.rs               跨进程更新互斥锁
│   ├── paths.rs              默认工作目录推导与可写性探测
│   ├── safety.rs             连续失败计数、安全模式与冷却
│   └── verify.rs             Ed25519 签名校验
├── models/
│   └── manifest.rs           清单数据结构与版本单调性判断
├── platform/                 各系统的文件替换实现
│   ├── mod.rs                统一入口 PlatformUpdater
│   ├── target.rs             平台标识（与 Tauri target 命名一致）
│   ├── shared.rs             跨平台辅助与启动确认
│   ├── unix_script.rs        macOS / Linux 共用的脚本模板
│   ├── windows.rs            Windows：PowerShell 脚本 + 提权 + 降权启动 + 回滚
│   ├── macos.rs              macOS：裸二进制（bundle 运行时回退）
│   └── linux.rs              Linux：裸二进制 + 提权/降权
├── updater.rs                高层封装：DeltaUpdater
└── bin/generate.rs           发布端命令行工具（clap，需 generator feature）
```

### 2.2 数据流

```
发布端                                        客户端
─────────────────────────────────────────────────────────────
generate.exe                                   DeltaUpdater::update()
  ├─ 读私钥                                        │
  ├─ 扫描 old_versions/                            ├─ 加互斥锁
  ├─ 为每个旧版本生成 .patch                       ├─ 清理历史临时文件
  ├─ 签名 latest.json                              ├─ GET latest.json
  ├─ 签名 安装包                                   ├─ GET latest.json.sig
  └─ 产出 latest.json / .sig / .pub                ├─ 验签清单
                                                    ├─ 匹配补丁
                     CDN                          ├─ GET patch（断点续传）
      ←──────────────────────────────               ├─ 校验 patch_hash
                                                    ├─ 应用补丁
                                                    ├─ 校验 target_hash
                                                    └─ 启动替换脚本 → 重启新版本
```

### 2.3 分层原则

- **`core/` 不含任何平台特定逻辑**，除 `platform/` 外全部可跨平台复用。
- **上层不重复实现下层的校验**。`apply_patch` 内部已做哈希校验，高层 `DeltaUpdater` 不会重复校验同一份数据。
- **错误一路向上传播**。核心路径不使用 `unwrap` / `expect`，线程崩溃转为 `DeltaError::WorkerFailed`。

## 3. 核心机制

### 3.1 补丁生成与应用的二进制差分

**生成**（`core/diff.rs::create_patch`）

```
1. 旧文件与新文件只读 mmap（按需分页，不一次性读入内存）
2. qbsdiff::Bsdiff 流式输出原始补丁到临时文件
3. zstd（level 19）流式压缩临时文件 → 最终补丁
4. 删除临时文件；任一步失败都不留半截产物
```

bsdiff 的原理：把新旧文件切成块，用后缀数组找到"新文件中与旧文件某段完全相同的部分"，只记录这些相同段的偏移与长度，其余差异部分单独存储。bsdiff 的原始输出（控制/差异/额外三股流）含大量可压缩字节——**不做二次压缩时补丁可能接近甚至超过全量包体积**（Deno 曾出现 147 MB 补丁大于本体的案例），因此最终补丁是 zstd 容器。

**效果**：20 MB 的可执行文件改动 1 MB，补丁仅约 210 字节（见 `tests/integration.rs::test_large_file_performance`）。

**关键实现细节**

| 细节 | 说明 |
|---|---|
| 512 MB 工作线程栈 | bsdiff 系列算法递归深度与文件规模相关，默认 2 MB 栈会栈溢出；不支持同进程并发多个补丁任务（栈是固定预留的） |
| 旧/新文件 mmap | 只读映射按需分页，峰值 RSS 远低于全量 read；映射期间文件不可被改写（更新锁保证） |
| zstd 压缩层 | 生成端 level 19；应用端按魔数嗅探，历史未压缩补丁原样透传，旧清单无需迁移 |
| 补丁只读一次 | 哈希校验（压缩形态）、目标大小预估（解压后）、实际应用共用同一份数据 |

**应用**（`core/diff.rs::apply_patch`）

```
1. 目标文件已存在 → 拒绝（TargetExists），不覆盖用户文件
2. 读取补丁（下载形态）→ 校验 SHA-256（锚定清单签名）
3. zstd 魔数嗅探：容器则解压，否则透传（兼容历史补丁）
   ——解压只发生在通过哈希校验的数据上，不存在解压炸弹风险
4. 从补丁头读出目标大小 → 检查磁盘空间
5. 工作线程：mmap 旧文件 → bspatch 合并 → 直接写入目标文件
6. 校验产物 SHA-256，不符则删除产物并报错
```

第 2 步和第 6 步构成**双端哈希校验**：补丁本身被篡改、或合并过程出错，都会导致最终产物哈希不符。

> **⚠️ 发布端兼容性**：当前 generate 产出的补丁是 zstd 容器；历史未压缩补丁
> 通过魔数嗅探仍可应用，旧清单无需迁移。

### 3.2 清单格式与平台隔离

清单是 Tauri 官方 `latest.json` 的超集：

```json
{
  "version": "0.2.0",
  "notes": "更新说明",
  "pub_date": "2026-11-05T08:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<安装包签名 base64>",
      "url": "https://cdn.example.com/Sereno_0.2.0_x64-setup.exe"
    }
  },
  "patches": {
    "windows-x86_64": [
      {
        "from_version": "0.1.0",
        "to_version": "0.2.0",
        "patch_url": "https://cdn.example.com/0.1.0_to_0.2.0.patch",
        "patch_hash": "<补丁 SHA-256>",
        "target_hash": "<产物 SHA-256>"
      }
    ]
  }
}
```

**为什么补丁必须按平台分组**

不同架构的安装包是**完全不同的二进制**，x86_64 与 aarch64 的补丁互不通用。若把所有补丁放在一个扁平列表里，x86_64 客户端可能取到 arm64 的补丁，`target_hash` 校验必然失败——用户看到"明明有补丁却更新失败"，且错误信息难以定位。

平台键命名与 Tauri updater 的 target **完全一致**（`windows-x86_64`、`darwin-aarch64`、`linux-x86_64` 等），因为 `platforms` 用的是同一套键，两边必须对齐。

**平台标识不要手写**

```rust
// 好：编译期确定，永不出错
manifest.find_patch(current_version, current_platform())

// 坏：手写可能拼错，且不报错，只是静默取不到补丁
manifest.find_patch(current_version, "windows-x86_64")
```

`current_platform()` 定义在 `platform/target.rs`，与 Tauri 的 `get_updater_target()` + `get_updater_arch()` 组合逻辑一一对应。

**兼容性**：`patches` 早期版本是扁平数组。读取时两种格式都接受（旧格式归入默认平台），因此历史清单不会导致解析失败。写入时统一使用分组格式。

**过期补丁防护**

`find_patch` 除了匹配 `from_version`，还要求 `to_version == manifest.version`。清单中可能残留其它平台上一轮发布的补丁，直接使用会把应用更新到**错误版本**。

### 3.3 签名体系：清单签名与安装包签名

引擎涉及**两份独立签名**，用途不同，缺一不可。

#### 3.3.1 清单签名（`latest.json.sig`）

**保护对象**：清单本身。

**为什么必须签**：清单里的 `patches[].target_hash` 决定"合并出来的文件是否正确"。若不签清单，中间人可以同时篡改 `patch_url` 与 `target_hash`，让客户端下载并执行任意程序。补丁哈希能发现内容被改，但**发现不了"攻击者换了一整套自洽的补丁与哈希"**。

只有对清单签名，才能把补丁的真实性锚定到一个客户端**内置**的公钥上。

**签名格式兼容**

minisign 的 `.sig` 文件有两种流传形态，验签函数都接受：

| 形式 | 来源 | `verify_manifest_signature` 行为 |
|---|---|---|
| base64 编码的 `.sig` 文本 | Tauri `latest.json` 的 `signature` 字段 | 自动 base64 解码后解析 |
| 原始 `.sig` 文本 | 磁盘上的 `latest.json.sig` 文件 | 直接解析 |

判定依据是 minisign 文件恒以 `untrusted comment:` 开头——这是精确判定，不是猜测。

**验签失败的处理**

```rust
verify_manifest_signature(&manifest_bytes, &signature, &public_key)?;
```

失败返回 `DeltaError::SignatureInvalid`，与 `HashMismatch`（文件损坏）明确区分。**签名失败意味着攻击**，必须直接阻断更新，绝不能降级为"忽略签名继续更新"。

**降级/重放防护：三层，默认全部开启**

签名合法 ≠ 版本正确。攻击者可以原样重放一份**旧的、签名合法的清单**，
把用户"更新"回包含已知漏洞的旧版本。

防线由三层共同构成：

1. **清单签名**：清单本身被 minisign 签名。攻击者无法把清单指向旧安装包
   而不破坏签名——这比"只签二进制字节、清单未签"的模型更强一层。
2. **版本单调性**：验签后按语义化版本比较 `manifest.version` 与
   `current_version`，不更高即返回 `UpdateOutcome::UpToDate`，
   绝不把旧安装包地址交给宿主。这是重放阻断的执行点。
3. **发布端一致性**：generate 把目标版本写进签名的 trusted comment
   （`tdu:v=<version>`），客户端校验"绑定版本 == 清单版本"，
   用于发现发布端"把 A 版本签名贴到 B 版本清单"的配置错误。

第 3 层单独不能替代重放防护（两边来自同一份签名材料，重放时仍然一致），
但它是纵深的一部分，不是"无效检查"；真正阻断重放的是第 1 + 2 层。
这三层**不依赖任何可选开关**，不需要发布端额外启用配置。

#### 3.3.2 安装包签名（`platforms[].signature`）

**保护对象**：全量下载的安装包。

这份签名供 **Tauri 官方 updater** 使用。发布端对安装包本身签名，填入 `platforms[target].signature`。这样：

- 走增量路径 → 本引擎负责校验
- 走全量路径 → 官方 updater 负责校验

两条路径都有完整性保障，官方 updater 完全无需改动配置。

> **重要**：`generate` 早期版本把 `platforms[].signature` 写死为 `"dummy_signature"`，导致**全量下载必定被官方 updater 拒绝**。现已修正为真实签名。

#### 3.3.3 公钥的分发

> 公钥必须**固化在应用里**（`tauri.conf.json` 或代码常量），**绝不能**从提供 `latest.json` 的同一台服务器下载。
>
> 否则攻击者可以同时替换清单与公钥，签名机制形同虚设。

`latest.json.pub` 只是给运维方便查看用的，客户端不应信任它——文件第一行
带 `DO NOT TRUST` 警告注释（写在 `untrusted comment:` 同一行内，保持解析兼容）。

### 3.4 下载与断点续传

**续传的正确性前提**

断点续传只有在服务端**明确返回 `206 Partial Content`** 时才安全。若服务端忽略 `Range` 头返回 `200` + 完整内容，而客户端盲目追加，结果是：

```
本地半截文件 (1000 字节) + 服务端完整文件 (4096 字节) = 5096 字节的损坏文件
```

更糟的是重试会再次追加，文件越滚越大。

**实现要点**（`core/downloader.rs`）

| 要点 | 处理 |
|---|---|
| 服务端返回 200 | 丢弃本地残留，重新完整下载 |
| 服务端返回 206 | 正常追加，此时 `Content-Length` 是**剩余字节数**，总量需加上已有部分 |
| 服务端返回 416 | 本地文件已不小于服务端，视为损坏，删除后重下 |
| 长度校验 | 已知总量时校验最终字节数，不符则删除并报错 |
| 重试退避 | 2s → 4s → 8s → 16s，最多 4 次 |
| 可重试判定 | 收敛在 `DeltaError::is_retryable()`，不靠字符串匹配 |

**只对"网络暂时不可用"重试**。`Timeout` 与 `Network` 可重试；`HttpStatus` 仅 5xx 与 429 可重试；校验失败、文件已存在等确定性错误立即返回——重试只会浪费时间并掩盖真正的原因。

**进度回调**

```rust
download_patch_with_progress(&client, &url, &path, |downloaded, total| { ... })
```

`total` 为 0 表示服务端未提供总长度（分块传输）。进度值单调不回退。

### 3.5 文件替换、启动确认与自动回滚

Windows 上无法直接覆盖正在运行的 exe。引擎的做法是生成一个脚本，由脚本在主进程退出后完成替换。

**完整流程**

```
主进程                     替换脚本(.ps1)                   新版本
  │                              │                              │
  ├─ 生成脚本                    │                              │
  ├─ 启动脚本                    │                              │
  ├─ 主进程退出 ────────────────→│                              │
  │                              ├─ 等待旧进程退出（按 PID）     │
  │                              │  （最多 60 秒）               │
  │                              ├─ exe → exe.bak              │
  │                              ├─ 新 exe → exe               │
  │                              ├─ 启动新 exe ────────────────→│
  │                              │                              ├─ 启动成功
  │                              │◄──── 写入成功标志 ────────────┤
  │                              ├─ 检测到标志                  │
  │                              ├─ 删除 exe.bak                │
  │                              ├─ 脚本保留，由下次更新清理回收│
  │                              │                              │
  │                     超时未收到标志：                      │
  │                              ├─ 结束新进程                  │
  │                              ├─ 删除新 exe                  │
  │                              ├─ exe.bak → exe（回滚）      │
  │                              ├─ 启动旧 exe ────────────────→│
```

**为什么用 PowerShell 而不是批处理**

批处理在这个场景下有多个实测复现的缺陷：

1. **cmd 按字节偏移读取批处理文件**，文件含 UTF-8 中文时偏移会错位，
   表现为后续命令被截断并报"不是内部或外部命令"。
2. **`cmd /c "<路径>"` 无法处理含 `&` `(` `%` 的路径**。实测四种写法
   （加引号、加 `call`、不加引号、切目录）只有"切目录 + 裸文件名"可用。
3. **批处理删除自身后 cmd 仍在读该文件**，读取随即错乱。
4. **`cmd` 的转义规则组合起来极易出错**：`set "VAR=值"` 按字面存储，
   但 `%VAR%` 展开时 `&` 会被当成命令分隔符、`^` 会被当成转义符。

PowerShell 用 `-LiteralPath` 处理路径（不做通配符与转义解释），
字符串用单引号字面量（只需把 `'` 转义成 `''`），上述问题全部消失。

**Windows 脚本的几个关键约束**

1. **脚本文件必须是 UTF-8 带 BOM**。Windows PowerShell 5.1 依赖 BOM 识别 UTF-8，
   无 BOM 时按系统 ANSI 代码页解析，中文会变成乱码并导致语法错误。
2. **等待旧进程退出要按 PID 判定**，不能靠"重命名是否失败"——
   Windows 允许重命名正在运行的可执行文件。
3. **回滚要按可执行文件完整路径结束进程**，不能按进程名批量结束，
   否则会连同用户手动打开的同名实例一起杀掉。
4. **提权后要重新执行整个脚本**：路径等信息是脚本自己算出来的，
   提权实例会重新计算一遍。
5. **脚本开头先做崩溃恢复**：上一轮若在"exe → .bak"之后、替换完成之前被打断
   （断电、进程被杀），exe 会缺失而备份还在。脚本检测到这种残缺状态时
   先还原备份，再开始本轮更新。

**macOS 与 Linux**

macOS 的 `.app` bundle 在运行时边界直接回退全量（见 3.8）——替换 bundle
内二进制只能 ad-hoc 重签（`codesign --sign -`），会丢失开发者身份与公证状态，
因此脚本不会走这条路径。bundle 外的裸二进制使用统一模板。

Linux 若目标目录不可写（例如通过 `.deb` 安装到 `/usr/bin`），
脚本优先用免密 `sudo -n` 重新执行自己（`-n` 不提示密码，避免无终端环境卡死），
失败后尝试 `pkexec`（桌面环境会弹图形授权框），并且只在有图形会话
（`DISPLAY`/`WAYLAND_DISPLAY`）时尝试、用 `timeout 30` 防止永久挂起。

**提权后必须降权**：提权进程启动的子进程会继承提权令牌。Windows 上经
`explorer.exe` 以登录用户拉起真正的 PE；Linux 上从 `SUDO_USER` /
`PKEXEC_UID` 推导原用户，用 `runuser -u` 启动，并把替换后的文件 `chown`
回原用户。否则"更新一次之后应用一直以管理员/root 运行"，下次手动启动
又恢复普通权限，行为不一致且扩大攻击面。

**进程等待与结束一律按 PID + 路径**，不用 `pgrep -x` / `pkill -x`：
Linux 的 `comm` 最长 15 字符（长应用名永远匹配不到）、缺少 procps 时
命令不存在会被当成"进程已退出"、同名实例会被误杀。Linux 额外用
`/proc/<pid>/exe` 校验路径，回滚时按可执行文件完整路径结束进程。

**所有失败路径统一重启旧版本**：提权被拒、备份失败、复制失败、哈希不符
都收口到 `Restart-Old` / `restart_old`。少了这一步，用户会看到"点了更新，
应用直接消失"。

**启动确认**

新版本启动成功后调用：

```rust
PlatformUpdater::confirm_startup_success()?;
```

它做三件事：解析目标工作目录、写入成功标志（让脚本保留新版本）、
清除连续失败计数。工作目录的解析顺序是：

1. 替换脚本写在 exe 旁边的 `tdx_update_dir` 指针（自定义 `work_dir` 时必需）；
2. 由可执行文件路径推导的用户缓存目录。

宿主也可以直接用实例方法 `updater.confirm_startup_success()`，
它直接使用配置里的 `work_dir`，不依赖指针。

**回滚是最后一道防线**。若新版本连启动都失败，脚本会恢复旧版本并重新启动它，用户不会卡在无法启动的状态。

### 3.6 并发互斥与失败计数（安全模式）

**互斥锁**（`core/lock.rs`）

用 `fs4` 的 `try_lock_exclusive` 实现跨进程互斥（fs2 已 unmaintained，
fs4 是其活跃维护分支）。多个实例同时启动时，只有一个能进入更新流程，
其余立即收到语义化的 `DeltaError::UpdateInProgress`。

**失败计数与安全模式**（`core/safety.rs`）

```
第 1 次更新失败 → 计数 = 1
第 2 次更新失败 → 计数 = 2
第 3 次更新失败 → 计数 = 3 → 达到上限
此后 update() 返回 UpdateOutcome::SafeMode，check() 返回 DeltaError::SafeMode
```

计数文件同时记录最后一次失败的 Unix 时间戳。达到阈值后进入 **6 小时冷却**：
冷却结束自动清零并放行一次新尝试；宿主也可以调用 `reset_safety()` 手动退出。
没有冷却的安全模式等于"永久禁用增量"，一次磁盘满就可能让用户再也走不了增量路径。
旧版只有一行计数的文件按"冷却已过期"处理，升级用户不会被永久锁死。

**只有确定性错误才计数**

暂态网络错误（超时、连接失败、5xx/429）不算——服务器抖动几次就把用户锁进
安全模式是误伤，这类错误由下载层的自动重试兜底。只有验签失败、哈希不符、
磁盘不足等确定性错误才累计；判定标准与 [`DeltaError::is_retryable()`] 一致。

**为什么计数不能被"清理"流程误删**

清理临时文件的逻辑在每次尝试更新前都会跑。若它一并删掉失败计数，计数永远归零，**安全模式形同虚设**。因此清理流程不碰计数与成功标志。

清理范围分**两个目录**，但**都只删本项目精确命名的文件**：

- `work_dir`：补丁、暂存文件、替换脚本、解压临时文件；
- `exe_dir`：`<目标 exe 文件名>.bak` 与工作目录指针。

早期实现按 `.bak`/`.old` 扩展名批量遍历，会误删用户自己的备份文件；
当前版本只删同名 `.bak`，并有回归测试锁定。替换脚本**不删除自身**——执行期间
删除正在被读取的脚本有竞态，残留脚本由下一次更新回收。

同理，**成功标志也不能被清理**——那是替换脚本判断是否保留新版本的依据，在替换流程进行期间删除它会导致误回滚。

### 3.7 磁盘空间与资源保护

**空间估算用补丁头，而非旧文件大小**

bsdiff 补丁头里直接记录了目标文件大小（`Bspatch::hint_target_size()`），比"旧文件大小 × 2"这种估算准确得多。

**路径解析容错**

`Path::new("merged.exe").parent()` 返回 `Some("")` 而**不是** `None`。若直接交给 `GetDiskFreeSpaceExW("")` 会失败，导致相对路径下的更新无法进行。实现会向上查找最近的存在目录并转为绝对路径。

**落盘而非堆内存**

补丁合并结果直接写入文件并预分配大小。200 MB 的安装包不会在内存中出现两份副本。

**补丁解压有上限且落盘**

压缩补丁先流式解压到临时文件，再只读映射给 bspatch——不把解压后的 bsdiff
流整个抱进内存。上限取 `旧文件大小 × 2 + 128 MB`，超过返回
`PatchExpandedTooLarge`（确定性错误）。早期 `decode_all` 会让压缩包与
解压流同时驻留，峰值可达 GB 级。

**工作目录必须用户可写**

补丁、暂存文件、替换脚本、日志与锁都放在**用户缓存目录**
（`%LOCALAPPDATA%/tauri-delta-updater/<应用名>-<路径指纹>`、
`~/Library/Caches/...`、`$XDG_CACHE_HOME/...`），不放在 exe 旁边。
`C:\Program Files`、`/usr/bin` 对普通用户只读，旧行为会让锁创建、
补丁下载、暂存写入全部失败，并在 3 次后锁进安全模式——而 UAC/提权
发生在更晚的替换阶段，永远到不了。

构造阶段用"创建探针文件"验证真实可写性，失败返回
`DeltaError::WorkDirNotWritable`，而不是等网络下载完才失败。

### 3.8 适用边界：哪些环境自动回退全量

判定函数 `incremental_fallback_reason(exe)` 只依赖运行环境（exe 路径与平台），
在**下载补丁之前**执行——清单仍会拉取（客户端要知道有无新版本与全量地址），
但不会为用不上的补丁消耗流量。判定为不适合时直接返回 `FallbackToFullDownload`；
`check()` 的 `has_patch` 也会尊重该判定（UI 不会展示"有补丁可下载"）：

| 环境 | 判定依据 | 为什么不能增量替换 |
|---|---|---|
| Linux AppImage | `APPIMAGE` 环境变量存在 | `current_exe` 指向 squashfs 临时挂载点（`/tmp/.mount_*`），替换出的文件随挂载卸载一起消失 |
| macOS `.app` bundle | 可执行文件祖先目录存在 `.app` | 替换 bundle 内二进制后只能 ad-hoc 重签，开发者身份丢失，Gatekeeper 与公证链路断裂 |
| Windows 单文件 exe | —（甜点区） | 始终适合增量替换；**但补丁只覆盖主 exe**（见下） |

**Windows 的边界必须显式知道**：补丁的基底与产物都是**主可执行文件**。
使用 `externalBin`（sidecar）或 `resources` 的应用，这些文件不在补丁范围内——
大版本升级若涉及 sidecar/resources 变更，增量产物是不完整的。
发布端会在补丁上写入 `"scope": "main_executable_only"`，客户端可据此
提示"本次增量不覆盖附加资源"。此类应用建议走全量下载。

**包管理器 / 安装器状态也不会同步**：直接替换 `app.exe` 后，
Windows 的 `Apps & Features` 仍显示旧版本、卸载器仍描述旧布局；
Linux 的 `dpkg` 数据库仍是旧版本，`apt upgrade` 可能把应用"降级"回去。
系统级部署应优先使用全量安装路径。

**为什么 macOS bundle 硬回退而不是继续实验**：ad-hoc 重签（`codesign --sign -`）
对开发者分发的应用是阻断性的，不是"实验性"能概括的。真正的可行解
（对整个 `.app` 做差分 + 客户端持有开发者证书重签）与"重建安装包"是
同一类工程问题，不值得在本路径上硬扛。bundle 外的裸二进制仍是实验性支持，
**不在支持承诺范围内**——发布前请在目标系统实测。

## 4. 接入方式

### 4.1 依赖

```toml
[dependencies]
tauri-delta-updater = "0.1"
```

> `generator` feature **默认关闭**，库使用者不再被迫编译
> `clap` / `regex` / `walkdir` / `chrono` / `minisign` / `windows-sys`。
> 只有需要发布端 CLI 时才显式启用：
> `tauri-delta-updater = { version = "0.1", features = ["generator"] }`。
>
> `rust-version = "1.88"`：这是 `reqwest 0.13 → url → icu_*` 依赖链的真实下限。
>
> 可选 `tracing` feature：启用后发出 `delta.check` / `delta.patch.matched` /
> `delta.fallback` / `delta.safety_mode.entered` / `delta.safety_mode.cooldown_active`
> 等结构化事件，默认不编译、零开销。

### 4.2 一行接入（推荐）

```rust
use tauri_delta_updater::{DeltaUpdater, UpdateConfig, UpdateOutcome};

let updater = DeltaUpdater::new(
    UpdateConfig::new(
        "https://cdn.example.com/latest.json",
        "BASE64_PUBLIC_KEY",     // 固化在应用里的公钥
    )
    .current_version(env!("CARGO_PKG_VERSION")),
)?;

match updater.update().await? {
    UpdateOutcome::Patched { staged } => {
        println!("已更新到 {}", staged.manifest().version);
        // 必须退出进程，否则替换脚本会判定失败并回滚
        std::process::exit(0);
    }
    UpdateOutcome::UpToDate { version } => {
        // 已是最新，或清单版本不高于当前版本（防降级重放分支）
        println!("已是最新版本 {version}");
    }
    UpdateOutcome::FallbackToFullDownload { full_download_url, reason } => {
        // 增量不可用（无补丁 / AppImage / macOS bundle）：
        // reason 是结构化的 FallbackReason，可直接 match 或展示
        let _ = (full_download_url, reason);
    }
    UpdateOutcome::SafeMode => {
        // 连续失败已达上限：提示用户手动下载
    }
    _ => {}
}
```

`DeltaUpdater::update()` 内部完成：加锁 → 清理 → 拉清单 → 验签 → 版本单调性
→ 匹配补丁 → 下载 → 校验 → 应用 → 启动替换脚本。

**双栈接入（与官方 updater 并存）**

```rust
// Cargo.toml 同时依赖：
// tauri-plugin-updater = "2"          ← 官方插件，负责全量
// tauri-delta-updater = "0.1"         ← 本库，负责增量
use tauri_plugin_updater::UpdaterExt;

match delta_updater.update().await? {
    UpdateOutcome::Patched { staged } => {
        // 本库已接管：不要调官方 updater，直接退出
        std::process::exit(0);
    }
    UpdateOutcome::FallbackToFullDownload { .. } => {
        // 本库的 UpdateLock 已随本次调用结束而释放，官方可安全接管。
        // endpoint/公钥配置完全不变——本库的清单是官方格式的超集。
        // 注意：官方 API 没有 block::block_on，异步上下文请直接用 .await；
        // 同步上下文用 tauri::async_runtime::block_on。
        app.updater_builder()
            .and_then(|b| b.build().ok())
            .and_then(|u| tauri::async_runtime::block_on(async move {
                let update = u.check().await.ok()??;
                update.download_and_install(|_, _| {}, || {}).await.ok()?;
                Some(())
            }));
        // 官方安装完成后按它的要求退出/重启
    }
    UpdateOutcome::UpToDate { .. } => { /* 已是最新，无需动作 */ }
    UpdateOutcome::SafeMode => { /* 提示手动下载 */ }
    _ => {}
}
```

要点：**本库 `Patched` 时绝不要再调官方 updater**（增量已完成，只差退出）；
**本库回退时才把控制权交回**——两条腿在同一份 `latest.json` 上各取所需。

**分阶段接入**

真实 UI 流程往往是"先发现新版本 → 用户确认 → 再下载"：

```rust
// 只拉清单，不下载任何东西
let info = updater.check().await?;

// 用户确认后下载并合并，但先不启动替换脚本
if let UpdateOutcome::Patched { staged } = updater.prepare().await? {
    println!("正在重启以完成更新...");
    staged.launch()?;          // 由宿主决定何时触发替换
    std::process::exit(0);
}
```

`UpdateConfig::auto_launch(false)` 可以让 `update()` 也不自动启动替换脚本。

**需要下载进度时**

```rust
updater.update_with_progress(|downloaded, total| {
    if total > 0 {
        println!("{downloaded}/{total}");
    }
}).await?;
```

**`UpdateConfig` 的可选项**

| 配置项 | 默认值 |
|---|---|
| `manifest_url` | 必填 |
| `signature_url` | `{manifest_url}.sig` |
| `public_key` | 必填 |
| `current_version` | 空（需设置；必须是语义化版本） |
| `platform` | `current_platform()` |
| `executable_path` | `None`（自动取当前进程的可执行文件） |
| `work_dir` | `None`（用户缓存目录，见 3.7；系统级安装不要指向 exe 目录） |
| `auto_launch` | `true` |
| `wait_timeout_secs` | `60`（等待旧进程退出） |
| `confirm_timeout_secs` | `60`（等待新版本启动确认） |
| `client` | `None`（使用默认客户端；自建时用 `client_builder()`） |

`DeltaUpdater::new()` 返回 `Result`：可执行文件路径无法确定、`current_version`
为空或不是语义化版本、工作目录不可写时直接报错，而不是在运行时静默退化。

### 4.3 分步调用

需要自行控制每一步时（自定义 UI 流程、复用已有网络层等），可直接使用底层 API：

```rust
use tauri_delta_updater::{current_platform, UpdateManifest, verify_manifest_signature};

// 1. 拉取清单与签名
let manifest_bytes = fetch_latest_json().await?;
let signature = fetch_latest_json_sig().await?;

// 2. 验签 —— 失败必须阻断更新
verify_manifest_signature(&manifest_bytes, &signature, &public_key)?;

// 3. 解析
let manifest: UpdateManifest = serde_json::from_slice(&manifest_bytes)?;

// 4. 版本单调性：签名合法只证明"出自发布者"，不证明"比当前新"
if !manifest.is_newer_than(current_version)? {
    return Ok(());
}

// 5. 匹配补丁（平台用 current_platform()）
if let Some(patch) = manifest.find_patch(current_version, current_platform()) {
    // 6. 下载（max_bytes 从 patch_size 推导，防止被灌盘）
    download_patch_with_progress(&client, &patch.patch_url, &patch_path, max_bytes, |d, t| {}).await?;
    // 7. 应用（内部会校验 patch_hash 与 target_hash，返回 VerifiedArtifact）
    let artifact = apply_patch(&exe, &patch_path, &staged_exe, &patch.patch_hash, &patch.target_hash).await?;
    // 8. 启动替换（脚本放用户可写的工作目录）
    let script = PlatformUpdater::generate_updater(&exe, &artifact, &work_dir)?;
    PlatformUpdater::launch_updater(&script)?;
}
```

### 4.4 启动时确认

```rust
// 应用启动成功后调用一次
PlatformUpdater::confirm_startup_success()?;
```

**这一步不能省**：它写入成功标志，替换脚本据此决定保留新版本还是回滚。省掉会导致新版本启动后被误判为失败并回滚。

自定义了 `UpdateConfig::work_dir` 时，使用实例方法
`updater.confirm_startup_success()`；静态方法会退回到 exe 旁边的
`tdx_update_dir` 指针（脚本启动新版本前写入）。

### 4.5 典型集成位置

```rust
// lib.rs
#[tauri::command]
async fn check_for_updates(app: AppHandle) -> Result<UpdateStatus, String> {
    let updater = DeltaUpdater::new(
        UpdateConfig::new(
            app_config().update_manifest_url.clone(),
            app_config().update_pubkey.clone(),
        )
        .current_version(app.package_info().version.to_string()),
    )
    .map_err(|e| e.to_string())?;

    match updater.update().await {
        Ok(UpdateOutcome::Patched { staged }) => {
            // 通知前端后退出进程，否则替换脚本会判定失败并回滚
            let _ = app.emit("update-ready", ());
            std::process::exit(0);
        }
        Ok(UpdateOutcome::FallbackToFullDownload { .. }) => Ok(UpdateStatus::FullDownload),
        Ok(UpdateOutcome::SafeMode) => Ok(UpdateStatus::ManualRequired),
        Ok(_) => Ok(UpdateStatus::NoUpdate),
        Err(e) => Err(e.to_string()),
    }
}

// main.rs，启动早期调用
fn main() {
    tauri::Builder::default()
        .setup(|app| {
            if let Err(e) = PlatformUpdater::confirm_startup_success() {
                eprintln!("启动确认失败: {e}");
            }
            Ok(())
        })
        .run(tauri::generate_context!())
        .expect("启动失败");
}
```

### 4.6 退出姿势：默认 `std::process::exit(0)`，上线前实测

替换脚本靠"旧 PID 消失"判定可以开始替换。接入了
`tauri-plugin-single-instance` 的应用尤其要注意：

- **不建议** `app.restart()`：它会先回到 Tauri 事件循环（触发
  `RunEvent::ExitRequested`）再重启，重启出的新实例会被 single-instance
  判定为第二实例，与替换脚本的"等待旧 PID 退出"逻辑产生竞态。
- **默认建议** `std::process::exit(0)`：旧 PID 确定性地消失，正是脚本等待的信号。
- **但 exit(0) 会跳过 Drop**，single-instance 插件的 socket/锁清理依赖平台
  行为——**上线前必须在每个目标平台实测一次完整更新**：确认新版本启动后
  不被误判为第二实例、也没有"旧实例卡住"。
- 若实测发现锁残留，改用：先 emit `update-ready` 给前端 → 前端稍等 →
  `app.exit(0)`，给插件一个清理窗口。
- 需要在退出前通知前端/UI 的，在调用 exit 之前做完（见 4.5 的 `update-ready`）；
  需要一步到位的用 `update_and_exit()`（Windows 弹 UAC 前先告知用户）。

## 5. 发布流程

### 5.1 构建工具

```bash
cargo build --release --features generator --bin generate
```

### 5.2 命令行用法

```bash
generate --old-dir <dir> --app-binary <file> --version <ver> --base-url <url> --private-key <key> [--installer <file>] [--existing <json>] [--password <pwd>] [--platform <key>] [--notes <text>] [--max-patch-ratio <f>] [--output-dir <dir>] [--dry-run]
```

| 参数 | 说明 |
|---|---|
| `--old-dir` | 历史版本**主程序**所在目录；为其中每个可识别的版本生成补丁 |
| `--app-binary` | 本次发布的**主程序**（补丁目标，决定 `target_hash`） |
| `--installer` | 本次发布的完整安装包；决定 `platforms.url` 与安装包签名。缺省退回 `--app-binary` |
| `--version` | 目标版本号，可带 `v` 前缀（会被规范化掉） |
| `--base-url` | 补丁与安装包的下载前缀 |
| `--private-key` | 私钥，见下；也可用 `TAURI_SIGNING_PRIVATE_KEY` 环境变量 |
| `--password` | 私钥口令；也可用 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` |
| `--existing` | 上一版 `latest.json`，用于保留其它平台的条目与补丁 |
| `--platform` | 目标平台标识；缺省从文件名推断，推断失败直接报错 |
| `--notes` | 更新说明 |
| `--max-patch-ratio` | 补丁体积占安装包的比例上限，超过则跳过（默认 1.0） |
| `--output-dir` | `latest.json` / `.sig` / `.pub` 的输出目录（默认当前目录） |
| `--dry-run` | 只规划与验证，不写文件 |

> **为什么主程序与安装包必须分开**：补丁基底与产物是**安装后的主程序**，
> 而 `platforms.url` / `platforms.signature` 指向**完整安装包**。NSIS/MSI
> 安装包与安装后的 exe 不是同一份字节，把安装包当补丁基底，
> 客户端在真实安装目录上应用时产物哈希必然不匹配。

**`--private-key` 接受三种形式**，本地开发与 CI 可用同一条命令：

- 指向密钥文件的路径
- base64 编码的密钥内容（Tauri CI 中 `TAURI_SIGNING_PRIVATE_KEY` 的格式）
- 密钥原文

### 5.3 产出物

| 文件 | 用途 | 是否上传 CDN |
|---|---|---|
| `latest.json` | 清单 | 是 |
| `latest.json.sig` | 清单签名 | 是 |
| `latest.json.pub` | 公钥（运维查看用） | 可选 |
| `*.patch` | 增量补丁 | 是 |
| 新版本安装包 | 完整安装包 | 是 |

### 5.4 GitHub Actions 示例

应用自身的发布流水线（在应用仓库里）大致如下：

```yaml
- name: Build CLI generator
  run: cargo build --release --features generator --bin generate

- name: Build application
  uses: tauri-apps/tauri-action@v0
  env:
    TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
  with:
    tagName: ${{ github.ref_name }}
    releaseName: ${{ github.ref_name }}

# 去掉 tag 的 v 前缀，与客户端上报的 CARGO_PKG_VERSION 保持一致
- name: Resolve version
  id: ver
  run: echo "version=${GITHUB_REF_NAME#v}" >> $env:GITHUB_OUTPUT
  shell: pwsh

- name: Download previous main executables
  run: |
    mkdir -p old_binaries
    # 历史版本要保存安装后的主程序（而不是安装包），否则补丁基底对不上
    aws s3 ls s3://${{ secrets.COS_BUCKET }}/binaries/ --endpoint-url ... \
      | Select-String -Pattern "Sereno_.*\.exe" | Select-Object -First 8 | ForEach-Object {
        $fileName = ($_ -split '\s+')[-1]
        aws s3 cp "s3://${{ secrets.COS_BUCKET }}/binaries/$fileName" "old_binaries/$fileName" \
          --endpoint-url ...
      }
  shell: pwsh

- name: Generate delta patches & signed manifest
  env:
    TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
  run: |
    .\target\release\generate.exe `
      --old-dir .\old_binaries `
      --app-binary .\target\release\Sereno.exe `
      --installer .\target\release\Sereno_${{ steps.ver.outputs.version }}_x64-setup.exe `
      --version ${{ steps.ver.outputs.version }} `
      --base-url https://${{ secrets.COS_BUCKET }}.cos.ap-beijing.myqcloud.com `
      --private-key "$env:TAURI_SIGNING_PRIVATE_KEY" `
      --existing .\latest.json `
      --output-dir .\dist
  shell: pwsh

- name: Upload to COS
  run: |
    aws s3 cp .\dist\latest.json s3://${{ secrets.COS_BUCKET }}/latest.json --endpoint-url ...
    aws s3 cp .\dist\latest.json.sig s3://${{ secrets.COS_BUCKET }}/latest.json.sig --endpoint-url ...
    aws s3 cp .\dist\latest.json.pub s3://${{ secrets.COS_BUCKET }}/latest.json.pub --endpoint-url ...
    Get-ChildItem -Path .\old_binaries -Filter "*.patch" | ForEach-Object {
      aws s3 cp $_.FullName "s3://${{ secrets.COS_BUCKET }}/$($_.Name)" --endpoint-url ...
    }
  shell: pwsh
```

> 补丁文件生成在 `--old-dir` 目录下，清单在 `--output-dir`，上传时注意路径。

### 5.5 生成的注意事项

- **主程序与安装包分离**：补丁基底/产物是主程序，全量地址与签名是安装包。
- **平台隔离**：只为与目标平台同架构、同操作系统的旧主程序生成补丁；
  推断失败直接报错，不会默认成 `windows-x86_64`。
- **平台条目总是刷新**：`platforms[target]` 始终指向本次发布的新安装包并附上真实签名。
- **发布端验证**：每个补丁都会先真实应用并校验产物哈希，通过才写入清单。
- **劣质补丁跳过**：`--max-patch-ratio` 控制补丁体积上限，超过则丢弃并记录日志。
- **历史补丁清理**：只保留目标版本与本次发布一致的补丁，避免清单膨胀。

| Windows 替换脚本真实执行（特殊字符、崩溃恢复、备份清理、哈希校验） | `windows_script.rs`，windows-latest |
| Unix 替换脚本真实执行（等待、备份、替换、成功标志） | `unix_script.rs`，ubuntu/macos |
| Linux 提权块与降权命令的**存在性** | `unix_script.rs` 的 Linux-only 静态断言（CI runner 非 root，无法真实走提权分支） |
| Windows 提权后 explorer 降权启动的**参数约束** | `windows_script.rs` 静态断言：只传目标路径、不附加工作目录 |
| `generate` 主程序/安装包分离、Linux 裸二进制、`--dry-run`、`--max-patch-ratio` | `generate_cli.rs`，三平台 |

自动化**无法**覆盖、需在目标机手动验证的部分：

1. 真实管理员/Root 提权后的降权启动（UAC / polkit 交互 + 进程令牌/所有者检查）；
2. 新版本启动失败时 60 秒超时回滚（需要真实等待窗口）；
3. 精简镜像缺少 `runuser` / `su` / `explorer.exe` 的环境。

这些边界已写入第 8 节「已知限制」，不作为隐性风险。

## 7. 故障排查手册

| 现象 | 可能原因 | 排查方向 |
|---|---|---|
| 总是走全量下载 | 平台标识不匹配 | 用 `current_platform()` 而非手写字符串；确认 `patches` 的键与 `platforms` 的键一致 |
| 总是走全量下载 | 目标版本不匹配 | `find_patch` 要求 `to_version == manifest.version`；确认清单版本号已更新 |
| 全量下载被官方 updater 拒绝 | 安装包签名无效 | 确认 `generate` 生成的 `platforms[].signature` 是真实签名而非占位符 |
| 验签总是失败 | 公钥来源错误 | 公钥必须是**应用内置**的，不能从服务器下载；检查 base64 是否完整 |
| 验签总是失败 | 签名格式不匹配 | 确认 `signature_url` 指向的是 `.sig` 文件；两种编码都支持，但内容不能被改写 |
| 下载中断后文件损坏 | 服务端不支持续传 | 已处理：服务端返回 200 时自动重下。可看日志确认 |
| 磁盘空间检查失败 | 路径解析异常 | 已处理相对路径；确认输出目录可写 |
| 替换失败 | exe 被占用 | 脚本会重试 60 秒；确认没有杀毒软件长期占用 |
| 替换超时秒数异常 | 脚本延时方式问题 | PowerShell 用 `Start-Sleep`，不要改回 cmd 的 `timeout` |
| 新版本被误回滚 | 未调用启动确认 | 启动早期调用 `confirm_startup_success()` |
| 主进程不退出导致回滚 | 宿主未结束进程 | 更新成功后必须退出进程，否则脚本判定失败并回滚 |
| 安全模式不生效 | 计数被清理 | 已修复；确认没有其它逻辑删除 `update_failures.txt`。安全模式有 6 小时冷却，冷却后会清零重试 |
| CI 发布中断 | 私钥格式 | 私钥参数支持路径 / base64 / 原文三种形式 |
| CI 发布中断 | 旧格式清单 | 已兼容旧扁平格式 |
| 补丁永远匹配不上 | 版本号格式不一致 | 清单版本号必须与客户端上报的 `CARGO_PKG_VERSION` 一致（都不带 `v`） |
| 一直走全量下载 | `current_version` 为空或非语义化版本 | 已在构造时拒绝：`DeltaUpdater::new` 返回 `Config` 错误 |
| `WorkDirNotWritable` | 工作目录只读 | 不要指向 `Program Files` / `/usr/bin`；省略 `work_dir` 用用户缓存目录 |
| `ResponseTooLarge` | 清单/签名响应超过 10 MB | 确定性错误，检查 CDN 是否被劫持或配置错误 |
| `ManifestInvalid` | 签名的清单本身格式错误 | 检查生成器输出的 JSON 与语义化版本号 |
| `UpToDate` | 清单版本不高于当前版本 | 正常分支；若期望更新，检查发布端版本号是否真的更高 |
| 更新后版本信息没变 | 绕过包管理器/安装器 | 直接替换 exe 不会更新 `dpkg` / `Apps & Features` 元数据；系统级部署用全量安装 |
| 更新"静默消失" | 用户取消了 UAC 提权 | 脚本已统一收口：记录日志并重新启动旧版本；见 `tdx_update.log` |
| `IncrementalNotApplicable` | 文件超过 2 GB 上限 | 增量更新不适用，走全量下载（`MAX_INCREMENTAL_FILE_BYTES`） |
| 工作目录残留 `tdx_update.ps1` / `.sh` | 正常行为 | 脚本不自删（避免执行期删除竞态），下一次更新的清理逻辑会回收 |

## 8. 已知限制

| 限制 | 说明 | 建议 |
|---|---|---|
| 仅单跳补丁 | 不支持 v1 → v3 的补丁链 | 跨版本请走全量下载 |
| 单文件 2 GB 上限 | bsdiff 的内存开销约为 max(17n, 9n+m)（n 为旧文件大小，m 为新文件大小），大文件会耗尽内存 | 超限返回 `IncrementalNotApplicable`，走全量下载（`MAX_INCREMENTAL_FILE_BYTES` 可关注后续调整） |
| 提权后等待重新计时 | Windows 脚本提权实例的 60 秒等待从零开始，最坏情况总等待 >90 秒 | 旧进程卡死时属于异常场景；正常情况下主进程退出在秒级 |
| 需完整旧文件 | 应用补丁时需要旧 exe 可被随机访问 | 旧文件走只读 mmap 按需分页，峰值 RSS 远低于全量读入；目标文件直接落盘 |
| macOS/Linux 实验性 | 仅 bundle 外的裸二进制；`.app` bundle 与 AppImage 运行时自动回退全量（见 3.8） | 生产环境请先在目标系统实测 |
| macOS 需重新签名 | 替换 bundle 内的二进制会破坏原有签名 | bundle 场景已自动回退全量，不在此路径上暴露 |
| 无自更新元数据 | 不拆分元数据与数据两阶段 | 体量敏感场景可自行扩展 |
| 需手动确认启动 | 不会自动判断"新版本是否健康" | 调用方在启动早期调用确认接口 |
| 补丁体积依赖相似度 | 二进制差异过大时补丁可能接近全量 | `--max-patch-ratio` 控制，超过阈值自动跳过 |
| 包管理器/安装器元数据不同步 | 直接替换 exe 不会更新 `dpkg` / `Apps & Features` 的版本信息，卸载器仍描述旧布局 | 系统级部署优先走全量安装 |
| 安装目录仍需提权 | 替换 `Program Files` / `/usr/bin` 下的文件需要管理员/root | 工作目录已移到用户缓存；提权被拒时会重新拉起旧版本 |
| 降权依赖系统工具 | Linux 降权优先 `runuser`，缺失时退回 `su`，两者都缺时记录日志并以当前身份启动；Windows 降权依赖 `explorer.exe` 代理（只能接收目标路径一个参数） | 精简镜像可能两者都缺，属环境限制；`explorer` 代理会丢失工作目录上下文，脚本已保证不传额外参数 |
| 安全模式可能误伤 | 连续 3 次确定性失败会暂停增量（冷却 6 小时后自动恢复） | 宿主可用 `reset_safety()` 提供"重试"按钮 |

## 9. 安全威胁模型

更新链路上每一环被篡改时的防线，以及残留风险：

| 攻击面 | 防线 | 残留风险 |
|---|---|---|
| 清单被替换（含自洽的补丁与哈希） | 清单 minisign 签名，公钥固化在应用内 | 私钥泄露则全线失守——私钥只存 CI secret，绝不下发 |
| 重放旧的合法清单（降级到漏洞版本） | 三层防线（见 3.3.1）：清单签名 + 验签后语义化版本单调性 + 发布端版本绑定；均默认开启，不依赖可选开关 | 若客户端 `current_version` 本身被外部篡改，单调性判据失效——版本号必须来自可信的包元数据 |
| 补丁在传输中被篡改 | 补丁 SHA-256（由已签名的清单锚定） | 无 |
| 校验完成到替换执行之间产物被替换 | `apply_patch` 返回携带 SHA-256 的 `VerifiedArtifact`；脚本复制前/后再校验一次 | 需要能写工作目录的同用户攻击者——此时本机已失守，属于威胁模型之外 |
| 更新后应用继承提权令牌 | Windows 经 explorer 以登录用户拉起；Linux 用 `runuser` 回到 `SUDO_USER`/`PKEXEC_UID` 并 `chown` 回原用户 | 依赖 `explorer.exe` / `runuser` 可用；缺失时记录日志并降级为当前身份启动 |
| 补丁响应体注入超大内容 | `patch_size`（签名锚定）推导上限；未声明时 512 MB 硬上限 | 无 |
| 清单/签名响应体注入超大内容 | 10 MB 上限 | 无 |
| HTTP 明文传输被窃听 | 内容经签名+哈希校验，篡改必然失败 | 泄露版本号等元数据；生产建议 HTTPS |
| 公钥与清单同时被替换 | 公钥必须内置，不从提供清单的服务器下载 | 宿主违反约定从服务器读公钥时全线失守 |
| 合并产物损坏 | 产物 SHA-256 与签名锚定的 `target_hash` 比对，不符即删 | 无 |
| 错误版本/错误架构的补丁 | `to_version == manifest.version` + 平台分组键 | 无 |
| 更新中途被打断（断电/被杀） | 产物落盘前不碰原文件；替换脚本开头做 `.bak` 崩溃恢复 | 无 |
| 清单签名接受 legacy 格式 | `allow_legacy = true`：generate 用 minisign 0.7 签名，0.7 可能产出 legacy 格式，验签端必须兼容 | 攻击面比官方 updater 0.3 语义略宽；发布端只用 minisign 0.7 生成签名，迁移新版 minisign 后应同步收紧为 `false` |

**设计原则**：任何校验失败都是硬失败——签名与哈希错误直接阻断更新并计入
安全模式，绝不静默降级为"跳过校验继续"。

**安全模式的语义边界**：安全模式可能由两类原因触发——安全阻断
（签名/哈希失败，意味着攻击或损坏）或持续性环境问题（磁盘满、权限不足，
属于 `!is_retryable()` 的确定性错误）。宿主应根据
[`DeltaError::is_security_blocking()`] 区分 UI 提示：
前者提示"更新已被阻断，请检查安全"，后者提示"清理磁盘/检查权限后重试"，
不要把所有 SafeMode 都展示为安全风险。

## 10. 后续结构性路线图（尚未实现）

以下三项是**结构性**改动，收益明确但投入大、风险高，本版本没有仓促集成。
它们需要独立分支 + 真实产物基准测试，而不是在主路径上边改边发。

### 10.1 PE 感知差分（Courgette / Zucchini 思路）

- **问题**：通用字节级 bsdiff 不理解 PE 结构。编译器/链接器版本、时间戳、
  节区布局的微小变化会造成大范围字节位移，补丁体积接近全量。
- **方向**：先反汇编/解析 PE，识别指针、相对地址等"位置敏感"字节，
  归一化后再差分，应用时反向修正。归一化必须是确定性的，
  因此不改变 `VerifiedArtifact` / 哈希锚定模型。
- **落地方式**：在 `create_patch` 前加一个可选预处理阶段，用 `generate`
  的 `--pe-normalize` 实验开关跑真实旧/新 exe 对比；只有在多个真实版本上
  稳定缩小补丁后才默认启用。**不建议**在没有基准数据时直接替换算法。

### 10.2 并行目录 / 原子切换

- **问题**：当前模型会短暂移动/覆盖目标 exe，回滚依赖 `.bak` 恢复。
- **方向**：新版本写到临时位置，用同卷 `MoveFileEx(MOVEFILE_REPLACE_EXISTING)`
  原子替换；旧文件从未被修改，回滚退化为"什么都不做"。
  这也能把 sidecar/resources 纳入不可变快照范围。
- **代价**：需要重新设计 `Staged` 生命周期与替换脚本，并验证
  "目标文件被独占锁定 / 跨卷 / 杀软占用"等边界。保留现有的崩溃恢复
  作为降级路径，而不是直接删除。

### 10.3 独立 `tauri-delta-core` crate

- **问题**：`core`、`platform`、`updater` 仍在同一个 crate，贡献者需要
  理解 Tauri 编排才能改算法；外部开发者难以只依赖核心逻辑做验证。
- **方向**：抽出不依赖 Tauri/HTTP/安装机制的纯逻辑 crate，
  `updater` 与 `platform` 变成薄适配层；核心流水线可在不启动应用的情况下
  做端到端单元测试。
- **代价**：workspace 拆分、公开 API 迁移与文档重写，属于 0.x 阶段的架构
  决策，建议与下一次破坏性版本一起做。

### 10.4 已提前完成的两项

- **发布端补丁自验证**：`generate` 对每个补丁**无条件**真实应用并校验产物哈希，
  通过才写入清单——不是可选 flag，坏补丁默认在 CI 失败。
- **“delta 从不 delta”路径断言**：端到端 MockServer 记录所有请求路径，
  增量命中的测试断言全量安装包 URL **从未被请求**。

### 10.5 本轮已完成的路线图项

| 项 | 状态 |
|---|---|
| 零配置入口 `DeltaUpdater::auto(url, pubkey, version)` | 已实现 |
| UI 语义默认路径 `install()` / `install_and_exit()` + `UpdateResult` | 已实现 |
| `CheckOutcome` 暴露 `is_delta` / `download_size` | 已实现 |
| `tracing` 结构化事件 + 独立事件断言测试 | 已实现 |
| `simulate_update` 本地闭环 + `examples/simulate_update.rs` | 已实现 |
| 发布端补丁自验证（默认开启） | 已实现（无条件） |
| MockServer 路径断言 / 安全守卫变异可捕获 | 已由现有测试覆盖 |
| `--zstd-level` 发布端压缩级别 | 已实现 |

### 10.6 为什么 Tauri 插件放在独立 crate

插件外壳本身不难，难的是依赖边界：

- `tauri` 会引入 WebView 相关依赖；Linux 需要 GTK/WebKit 系统库，
  macOS 需要系统框架。把插件放进本 crate 并开启 `tauri` feature 后，
  CI 的 `--all-features` 在 ubuntu/macos 上会需要安装这些系统库，
  否则整条矩阵变红。
- 插件应该是薄壳：只做注册、命令、权限与事件桥接，不包含更新逻辑。
  它最适合作为独立的 `tauri-plugin-delta-updater` crate，依赖本 crate 的
  `auto` / `install` / `UpdateResult`，并单独配置 CI。

因此本轮先完成“默认路径变窄”与“可观测”，插件留到独立 crate 的阶段。
